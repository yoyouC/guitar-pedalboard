# 私有双桶社区写限流

发布、修订、点赞和举报各自使用独立策略，并且一次写操作必须同时取得成员桶和网络来源桶的容量。成员桶防止单一账号突发滥用，网络来源桶限制跨账号突发；任一桶不足时两个桶都不扣减。服务返回稳定的 `write_rate_limited`、操作类型、`Retry-After` 和绝对 `retryAt`，具体速率与突发阈值仅由部署配置决定，不进入公开 API 承诺。

生产适配器在事务内先锁定活动成员，再确保两个桶存在、锁定并原子更新，避免首次并发请求各自获得完整突发容量，也避免注销清除后并发写入重新创建成员桶。成员 id 与代理提供的首个网络来源只在进程内计算 SHA-256，数据库只保存散列；永久注销事务删除成员桶，完全回填且超过策略所需空闲窗口的成员与网络桶由后续同类写入清理。网络来源用于滥用控制，不构成公开身份或行为分析资料。策略解析限制桶容量与最长完全回填窗口，适配器返回的异常重试时间在响应边界回退为稳定的有界 `429`。

新作品发布、声音修订追加（包括从历史修订复制回退）和普通举报还要求登录身份具有已验证邮箱；注销恢复也要求本次恢复身份明确完成邮箱验证。拒绝响应提供站内验证入口；官方客户端在原表单仍挂载时打开验证面板，并保留编辑状态及验证或重试反馈。验证邮件只能通过绑定当前会话邮箱的专用包装端点发送：包装层拒绝匿名请求、忽略客户端邮箱并从会话派生收件人，发送器使用独立的验证邮件文案，不能借验证流程切换身份。限流只位于写路径：公开读取、已加载内容和本地音频不访问限流存储，因此限流存储故障最多令相关社区写操作暂时不可用。

验收测试通过发布、修订、点赞和举报 API 观察验证与限流行为。散列不落明文、注销清除成员桶及首次并发仲裁属于无法从公开响应直接证明的窄安全/并发不变量，允许在 PostgreSQL 集成测试中检查存储边界；这些检查不替代 API 黑盒验收。
